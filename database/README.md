# База данных «Гостиница»

[Главная страница](../README.md) · [Модели данных](../docs/02-data-models/README.md)

PostgreSQL 18, база `hotel_booking_web`, схема `public`. Установка создает десять таблиц, ограничения, триггеры, три представления и функции чтения. Пользователь SQL-сеанса становится владельцем создаваемой базы; имена и пароли локального сервера в файлы не записываются.

## Подготовка

Запустите сервер в Postgres.app. Для терминала macOS добавьте клиентские программы в путь:

```sh
export PATH="/Applications/Postgres.app/Contents/Versions/latest/bin:$PATH"
psql --version
```

В других установках достаточно доступных в `PATH` команд `psql`, `createdb` и `dropdb`. Нужны PostgreSQL 18+, право создания базы и право установки двух расширений в новой базе. Скрипты не меняют настройки аутентификации сервера и не создают глобальные роли.

Команды запускаются из корня репозитория. По умолчанию используется текущая локальная учетная запись. Если ваша установка требует иной адрес или пользователя, задайте `PGHOST`, `PGPORT` и `PGUSER` в своем окружении; учетные данные не добавляются в Git.

## Установка

```sh
psql -X -d postgres -v ON_ERROR_STOP=1 -f database/00_create_database.sql
```

Создается только база `hotel_booking_web`. Если она существует, повторного создания нет. Внутри установленной схемы v1 не выполняется повторное создание таблиц, а образцы добавляются только при отсутствии своих ключей. Существующие данные, стоимость броней и хеши пользователей не перезаписываются.

Частично установленная или конфликтующая схема не исправляется удалением объектов: выполнение останавливается с ошибкой. Начальная миграция находится в транзакции; следующие версии следует добавлять отдельными миграциями. Маркер `hotel_booking_web:schema:v1` хранится в комментарии схемы; при повторе проверяется наличие десяти таблиц и exclusion-ограничения. Это простой установщик этапа моделирования, не полноценный механизм миграций приложения.

## Просмотр и запросы

```sh
psql -X -d hotel_booking_web
```

В интерактивном `psql`:

```sql
\dt
SELECT * FROM find_available_rooms(hotel_today()+30, hotel_today()+33, 2);
SELECT reference, status, planned_amount FROM v_booking_details;
SELECT * FROM v_stay_history;
SELECT * FROM v_cleaning_queue;
```

Готовые сценарии чтения и пример рабочего цикла:

```sh
psql -X -d hotel_booking_web -v ON_ERROR_STOP=1 -f database/03_queries.sql
psql -X -d hotel_booking_web -v ON_ERROR_STOP=1 -f database/04_report.sql
psql -X -d hotel_booking_web -v ON_ERROR_STOP=1 -f database/05_workflow_example.sql
```

Последний файл откатывает все свои строки. Последовательности IDENTITY могут получить пропуски; это нормальное свойство PostgreSQL и не означает потери записей.

## Демонстрационный набор

Создаются пять ролей и пять вымышленных пользователей с адресами `example.invalid`. BCrypt-хеш каждого пользователя получен из случайного значения, которое не сохраняется. Публичного демонстрационного пароля нет; вход в веб-приложение будет реализован отдельно.

Три типа номеров: одноместный на одного гостя за 2 500 рублей, двухместный на двоих за 4 000 рублей и семейный на четверых за 7 000 рублей. Шесть комнат: `101`, `102`, `201`, `202`, `301`, `302`.

При первой загрузке даты отсчитываются от дня гостиницы:

| Заказ | Сценарий |
|---|---|
| `DEMO-CLOSED-001` | Номер 101: выезд в день заезда, начисление 4 000 рублей, ожидается уборка |
| `DEMO-ACTIVE-001` | Номер 102: действующее проживание, плановый выезд через две ночи |
| `DEMO-FUTURE-001` | Номер 301: будущая бронь через семь дней на три ночи |

Повторный запуск сохраняет эти даты и состояния, а не переносит их на новый день. Со временем активное демонстрационное проживание станет просроченным; это корректный пример удержания номера до выезда.

Уведомления только ставятся в таблицу очереди. SMTP-клиента на данном этапе нет, письма не отправляются.

## Проверка

```sh
python3 database/tests/run_tests.py
```

В нестандартной установке можно задать каталог клиентских утилит:

```sh
PG_BIN=/path/to/postgresql/bin python3 database/tests/run_tests.py
```

Исполнитель использует только стандартную библиотеку Python и клиентские программы PostgreSQL. Создается новая база вида `hotel_booking_web_test_` и восемь случайных шестнадцатеричных символов. Существующая база не переиспользуется. В `finally` удаляется только база, успешно созданная этим запуском; рабочая база и данные других проектов не изменяются.

Последовательность: установка с нуля → 51 проверка с `ROLLBACK` → точное сравнение исходных строк → повтор установки → сравнение строк → две конкурирующие транзакции. Первая сохраняет заказ, вторая получает SQLSTATE `23P01`; после этого одноразовая база удаляется.
